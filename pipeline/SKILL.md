# Codebase Knowledge Wiki

You are a **writer** compiling a wiki about a software system from its own repository.
Not a documentation generator. A writer. Your job is to read source units, understand
what the system does and why, and write articles that capture that understanding.

This is a fork of the personal-wiki skill. Three things are different, and they are
the whole point:

1. **Sources are code, and code can be checked.** Every claim gets a grade. An
   ungraded wiki about a codebase is a plausible-sounding liability.
2. **Entries have no dates of their own**, so the ingest step assigns each unit the
   commit date it first appeared. Absorbing chronologically then replays how the
   system was built, which is the only order that makes rival implementations legible.
3. **Sources move.** A wiki article about a diary entry stays true forever. An
   article about `src/api` is stale the moment someone merges. Drift handling is
   mandatory, not optional.

## Quick Start

```
/wiki ingest        # Turn the repo into raw/entries/ (runs scripts/ingest.py)
/wiki absorb all    # First run: compile every entry, oldest first
/wiki absorb        # Later runs: absorb the queue in raw/_pending.md
/wiki query <q>     # Ask questions; answers cite path@sha
/wiki verify        # Re-check graded claims against current code
/wiki cleanup       # Audit and enrich existing articles
/wiki breakdown     # Find and create missing articles
/wiki status        # Show stats, including grade distribution
```

This skill lives in the repo at `.cursor/skills/wiki/` (project-local, not global).
Ingest command:

```bash
python .cursor/skills/wiki/scripts/ingest.py --repo . --out raw/entries
python .cursor/skills/wiki/scripts/graph_verify.py          # after verify / when graph exists
python .cursor/skills/wiki/scripts/graph_verify.py --gaps   # ranked hubs with no wiki coverage
```

## Graphify vs wiki

This repo has two knowledge layers. Use both; do not duplicate one into the other.

| Layer | Artifact | Answers |
|---|---|---|
| **Graphify** | `graphify-out/graph.json` (+ CLI) | What exists *now*: symbols, imports, calls, paths, god-nodes |
| **LLM wiki** | `wiki/**/*.md` | Why / history / decisions / tensions / ops meaning / non-code intent |

**Editorial rule:** if a claim is fully recomputable from the graph (call graph, import edge, symbol existence), prefer a `graphify` query over freezing it as wiki prose. Wiki sentences should annotate what the graph cannot derive — product intent, which backend is live, diagram meaning, unresolved tension.

**Corpus alignment:** keep repo-root `.wikiignore` and `.graphifyignore` in sync for shared excludes (`backend/`, `Asset-Manager/`, `raw/`, `wiki/`). `graphify-out/` is gitignored; regenerate with `graphify update .` or `graphify extract .`.

**Query surface for scripts/agents:**

```bash
graphify query "..." --graph graphify-out/graph.json
graphify explain "PdpRunRequest"
graphify path "A" "B"
graphify god-nodes --json
# dump: graphify-out/graph.json  (nodes + links — best for automation)
```

## What This Wiki IS

A knowledge base covering one system's entire surface: services, modules, domain
entities, workflows, data contracts, deployment, and the decisions and unresolved
tensions behind all of it. Like Wikipedia, but the subject is one codebase.

The question is never "what does this file contain?" It is: **"what does this mean,
what does it connect to, and how sure am I?"**

## Directory Structure

```
your-repo/
  <the code>              # the raw layer. NEVER modified by the wiki.
  raw/entries/            # one .md per source unit (generated by ingest.py)
  raw/_manifest.json      # unit → sha + status, for drift detection
  raw/_pending.md         # absorb queue: new / changed / removed since last ingest
  wiki/
    _index.md
    _backlinks.json
    _absorb_log.json
    _grades.json          # claim grade rollup per article
    {directories}/
```

`raw/entries/` is derived and disposable. Regenerate it, never hand-edit it.
Articles cite the **original** `path@sha`, never the entry file.

## Command: `/wiki ingest`

Run `.cursor/skills/wiki/scripts/ingest.py`. Do not write your own walker and do not read the repo file by file.

The script exists because the mapping from repo to entries is not one file per entry.
2,479 tracked paths become ~250 units:

| Unit kind | Rule |
|---|---|
| `doc` | Each `.md`/`.rst`/`.txt` is its own entry. Highest signal per token. |
| `binary_doc` | `.docx`/`.pptx`/`.pdf`/`.xlsx` extracted to text via pandoc/markitdown/pdftotext. |
| `diagram` | `.excalidraw` text labels pulled out of the JSON in reading order. |
| `code_package` | Code is **never** one entry per file. A package becomes one entry containing a generated fact sheet: file list, LOC, HTTP surface, declared symbols, import graph, test count, and — when `graphify-out/graph.json` exists — **cross-package edges** (below). Packages over `--max-package-files` (120) split deeper, so `src/application` becomes `application/arps`, `application/economics`, … rather than one 208-file blob. |
| `runtime_contract` | compose files, CI workflows, nginx conf, pyproject, `.env.example`. Small and high-signal — these describe what actually runs. |
| `dataset` | A directory of 5+ data files becomes one entry with a schema summary, not 500 entries. |

Excluded outright: tool caches, images, lockfiles, generated migrations (hardcoded
in `ingest.py`).

**Project excludes** live in a repo-root `.wikiignore` (gitignore-lite). Edit that
file to skip folders/files without changing the skill. Keep `.graphifyignore`
aligned with the same trees. A typical repo's defaults exclude `backend/`,
`Asset-Manager/`, `raw/`, `wiki/`, and `graphify-out/`.

```gitignore
# .wikiignore examples
backend/
Asset-Manager/
raw/
wiki/
*.lock
**/local_outputs/**
```

Syntax: `#` comments, `dir/` prefixes, exact paths, and `*` globs. Hardcoded
`EXCLUDE_DIR` / `EXCLUDE_EXT` still always apply.

After changing `.wikiignore`, re-run ingest. Units that disappear land in
`raw/_pending.md` under **removed** — absorb/verify to clean wiki articles.

Frontmatter carries `path`, `sha`, `first-seen date`, `last_touched`, `commits`,
`authors`, and `status`. **`status: superseded`** is set mechanically for version
chains (`API_v1/v2/v3`), backup folders, and `* copy` files.

The script also writes `raw/_pending.md` — the absorb queue, computed by diffing
against the previous run's manifest. That file, not a date range, is what drives the
next absorb.

### The fact sheet is an itinerary, not content

When `graphify-out/graph.json` is present, each `code_package` entry carries three
extra fields derived from the graph's call/import edges:

```
**Called by:**  application/workflows(13), application/economics(4), …
**Calls into:** domain/decline(6), constants(2), …
**Open next** — what the rest of the system actually calls:
- `run_arps()` — `application/arps/service.py:L90` ← 7 external via run.py, per_well_fit.py
```

These exist because the import histogram keys on `mod.split(".")[0]`, which cannot
say which package a symbol came from and never says who calls in. Without them a
package reads as an island, no flow can be traced, and the writer falls back on
whatever doc narrates it — measured at **2% code-grounded** for `module` articles
before this was added, against 100% for `contract` (a compose file needs no
traversal).

**Use them to decide what to open, never as claims.** Rule 11 still holds: an
article must not assert "arps is called by workflows" — that is recomputable, so
query it, or it goes stale silently and nothing catches it. Open the listed entry
points, read them, and grade what you find there.

If the graph is missing (fresh clone, CI — `graphify-out/` is gitignored) these
fields are simply absent. Refresh it with `scripts/graphify-refresh.sh`; a
`post-commit` hook does it automatically on `dev` via `scripts/install-hooks.sh`.

`built_from_commit` in the entry frontmatter records the revision the entry
describes. Articles absorbed from it should carry the same field.

Before absorbing, check the run summary for binary docs that failed extraction. An
entry whose body says `EXTRACTION FAILED` must not be absorbed — absorbing it teaches
the wiki that a document contains nothing.

## Command: `/wiki absorb [queue|all|date-range]`

**Default is `queue`, not a date range.** Read `raw/_pending.md` and absorb exactly
what it lists. Date ranges are the parent skill's trigger and they are unsafe here:
when a file is added inside an existing code package, the package entry keeps its id
and its date-prefixed filename — only the body and sha move. A date-range absorb sees
nothing. A month of new code can land with no signal at all.

The queue has three buckets:

- **new** — never absorbed. Normal path.
- **changed** — the sha or the status moved. These are already marked done in
  `_absorb_log.json`. **The queue overrides the log.** Re-read the entry, re-absorb,
  and re-grade every article citing that path. A unit also lands here when a newer
  version demotes it to `superseded` — its bytes never changed, but every present-tense
  claim sourced from it is now wrong.
- **removed** — gone from the repo. Articles citing it are dead. Rewrite or delete them.

Renames are a known blind spot: without `--follow`, a renamed file appears as a
`removed` plus a `new` dated today. Check the queue for that pairing before absorbing,
or you will get a duplicate article.

Same loop as the parent skill: one entry at a time, chronological, read `_index.md`
before each, re-read every article before updating it. Non-negotiable.

Chronological here means **by first-seen commit date**, so the absorb pass reconstructs
the system's history. This matters more than it sounds. When a repo contains two rival
implementations, absorbing them in date order produces an article about a *migration*.
Absorbing them alphabetically produces an article about a system that does not exist.

For each entry:

1. **Read the entry.** For a `code_package`, the fact sheet tells you what the package
   is; open two or three actual files to learn what it *does*. For a `diagram`, the
   extracted labels are a flow — follow it.
2. **Understand what it means.** A 12-line config file and a 200-file package need
   different attention. A `runtime_contract` often settles a question three docs argue about.
3. **Match against the index.**
4. **Update and create articles**, integrating rather than appending.
5. **Grade every claim as you write it** (below). This is the step people skip and
   it's the one that makes the wiki usable.
6. **Connect to patterns.** A convention appearing across five packages is an article.

### Rule: every claim is graded

Grades live inline as a trailing tag, and roll up into frontmatter.

| Grade | Meaning |
|---|---|
| `[verified: path@sha]` | Asserted in a doc **and** confirmed in code you opened. |
| `[code: path@sha]` | Read from code. True at that sha; nobody wrote it down. |
| `[doc: path@sha]` | Asserted in a doc, not checked against code. May be aspirational or stale. |
| `[conflict]` | Doc and code disagree. Record both. Resolve nothing silently. |
| `[gap]` | A known unknown. |

An article that is mostly `doc` is a lead, not a reference. An article with no `gap`
entries is probably lying about how much it knows. `[conflict]` is a finding, not a
failure — in an undocumented codebase it is often the most valuable line on the page.

### Rule: superseded entries never ground present-tense claims

Absorb them into `history/` and `decisions/` only. If a superseded entry is the only
source for a claim about current behaviour, the claim is a `[gap]`.

### Anti-cramming / Anti-thinning

Unchanged from the parent skill, with one codebase-specific trap: the pull is to write
one article per directory. Directories are not concepts. `src/application` is not an
article; "ARPS decline-curve forecasting" is.

### Every 15 Entries: Checkpoint

1. Rebuild `_index.md` and `_backlinks.json`.
2. New article audit — zero new articles in 15 means you're cramming.
3. **Grade audit.** What fraction of claims are `verified` vs `doc`? If `doc` exceeds
   half, you are transcribing documentation, not building knowledge. Go open code.
4. Quality audit on the 3 most-updated articles. If any reads like a file listing,
   rewrite it.
5. Split anything over 150 lines.

## Command: `/wiki query <question>`

As the parent skill, with one rule inverted.

The parent says never read raw entries during query. **Here you may, and sometimes
must.** If the answer turns on a `doc`-graded or `conflict`-graded claim, open the
cited `path@sha` and check. Then upgrade the grade in the article — a query that
verifies a claim should leave the wiki better than it found it.

Answers cite `path@sha`, never article names alone. If the wiki doesn't cover it, say
so and name which package would need reading.

**Compose with graphify** when the question is structural or a pipeline “how”:

1. Run `graphify query` / `explain` / `path` for the live call/import skeleton.
2. Read the matching wiki article(s) for grades, product intent, and conflicts.
3. Answer = graph skeleton + wiki annotations. Do not invent call edges the graph
   does not show; do not omit wiki `[conflict]` / `[gap]` that the graph cannot know.

| Query type | Where to look |
|---|---|
| "How does X work?" (pipeline) | `graphify explain` / `query` first, then `modules/` / `workflows/` |
| "What calls / imports X?" | `graphify` only (unless wiki has non-structural context) |
| "Where is X handled?" | `_backlinks.json`, `services/`, `modules/`; confirm with graph |
| "Why is it built this way?" | `decisions/`, `tensions/`, `history/` (wiki; graph optional) |
| "What talks to Y?" | `graphify path` / `query`, then `integrations/`, `contracts/` |
| "What breaks if I change Z?" | `graphify affected "Z"`, backlinks, `contracts/` |
| "What don't we know?" | `gaps/`, `_grades.json`, plus `graph_verify.py --gaps` |

## Command: `/wiki verify`

New. There is no equivalent in the parent skill because diary entries don't change.

1. Run `python .cursor/skills/wiki/scripts/ingest.py --check`, or read
   `raw/_pending.md` from the last ingest. Both report every unit whose sha or
   status moved.
2. Run `python .cursor/skills/wiki/scripts/graph_verify.py` (requires
   `graphify-out/graph.json`). Read `wiki/_graph_verify.json` for suggested
   demotions: code paths cited in `[verified]` / `[code]` / `[doc]` tags that
   no longer appear in the graph → treat as candidates for `[gap]` or `stale`.
   Do **not** auto-edit articles; apply demotions yourself after confirming.
3. For each moved unit (and each graph demotion you accept), find articles citing
   it (`_backlinks.json` + grep for the path).
4. Mark those articles `stale: true` in frontmatter.
5. Re-open the code (and/or trust the graph for symbol existence). For each
   affected claim: still true → bump the sha. No longer true → rewrite and
   regrade. Can't tell → downgrade to `[gap]`.
6. An article stale through two verify cycles gets flagged for deletion. A
   confidently wrong reference is worse than a missing one.

Run this after every pull. It is the whole reason the sha is in the frontmatter.
SHA drift catches “the file changed”; the graph pass catches “the symbol/path is
gone from the structural index.”

## Command: `/wiki breakdown`

Find missing articles and expand coverage. Prefer justified gaps over vibes:

1. Read `wiki/_index.md`, `wiki/_grades.json`, and existing `gaps/`.
2. Run `python .cursor/skills/wiki/scripts/graph_verify.py --gaps` and open
   `wiki/_graph_verify.md` (hubs with high degree and no wiki mention).
3. Create or extend articles for the highest-signal uncovered hubs — concepts and
   workflows, not one article per directory.
4. Rebuild `_index.md` / `_backlinks.json` when done.

## Directory Taxonomy

Directories emerge from the data. Don't pre-create them. Several categories carry
over from the parent skill unchanged, because they turn out to describe systems as
well as they describe people.

### Structure

| Directory | What goes here |
|---|---|
| `services/` | Independently deployable pieces |
| `modules/` | Named units of logic within a service |
| `packages/` | Code packages that don't map cleanly to a named module |
| `entities/` | Domain nouns — the things the system is *about* |
| `workflows/` | End-to-end paths through the system |
| `contracts/` | API surfaces, schemas, event shapes, DB tables |
| `integrations/` | External systems and third parties |
| `datasets/` | Data the system carries, with provenance |

### Operation

| Directory | What goes here |
|---|---|
| `ops/` | Deployment, CI, environments, infra |
| `runtimes/` | How a thing actually runs — ports, processes, schedules |
| `incidents/` | Things that broke, if the repo records them |

### Reasoning — inherited, and the most valuable directories here

| Directory | What goes here |
|---|---|
| `decisions/` | Inflection points with enumerated reasoning. Effectively ADRs, recovered from commits and docs. |
| `tensions/` | Unresolved contradictions between two valid approaches. Two rival implementations is a `tensions/` article, not two `services/` articles. |
| `patterns/` | Recurring conventions with a trigger, a mechanism, an outcome |
| `history/` | Phases the system passed through. The parent skill's `eras/`. |
| `gaps/` | What is not known and what would need reading to find out |

`people/` survives too: `git log` names authors, and "who owns this" is a real
question the wiki can answer.

## Writing Standards

### The Golden Rule

**This is not documentation for the library. This is about the library's role in
this system.** A page about Postgres isn't a Postgres tutorial. It's which tables
exist, who writes them, what breaks when the schema changes here.

### Tone

As the parent skill: Wikipedia-flat, one claim per sentence, attribution over
assertion, dates and specifics instead of adjectives. No em dashes, no peacock words,
no editorial voice, no "would go on to."

One addition: **never write in the aspirational present.** "The service validates
input" is a claim requiring a grade. "The service is designed to validate input" is
a doc paraphrase pretending to be a fact. If you can't grade it, don't assert it.

### Snippet discipline

Replaces the parent skill's quote discipline. Maximum 2 code snippets per article,
10 lines each, each carrying `path@sha`. Snippets are evidence, not content. If an
article is mostly code, you haven't understood it yet — you've pasted it.

### Article Format

```markdown
---
title: Article Title
type: system | domain | flow | boundary | runtime | decision | conflict | unknown | idea | outcome
created: YYYY-MM-DD
last_updated: YYYY-MM-DD
stale: false
grades: {verified: 8, code: 4, doc: 3, conflict: 1, gap: 2}
sources: ["backend_new/src/application/arps@a1b2c3d", "backend_new/docs/modules/07_arps.md@e4f5a6b"]
related: ["[[Other Article]]"]
---
```

### Length targets

| Type | Lines |
|---|---|
| Module / package | 40–80 |
| Entity | 30–60 |
| Workflow | 60–120 |
| Contract | 30–70 |
| Decision / tension | 40–70 |
| Service | 60–100 |
| Gap | 15–30 |
| Minimum | 15 |

## Principles

1. **You are a writer.** Understand the system, then write about it.
2. **Every claim carries a grade.** Ungraded prose about code is a liability.
3. **`[gap]` and `[conflict]` are findings, not failures.** In an undocumented
   codebase they are often the most valuable lines on the page.
4. **Code is the tiebreaker, docs are the hypothesis.** When they disagree, record
   both and grade it `[conflict]` — but never let a doc override what the code does.
5. **Superseded sources explain history, never behaviour.**
6. **Directories are not concepts.** Write about what the system does, not where
   the files live.
7. **Cite `path@sha`, always.** A citation without a sha cannot go stale, which
   means it cannot be trusted.
8. **Re-ingest after every pull, and absorb by queue.** Adding is safe; *changing*
   is what rots the wiki, and only the queue sees it.
9. **Read the diagrams.** Extracted flow labels often encode intent no doc states.
10. **Two rival implementations are one `tensions/` article**, until a human rules.
11. **Graphify holds structure; the wiki holds judgment.** Do not freeze call graphs
    in articles — query them. Annotate what the graph cannot know.

## Concurrency Rules

- Never delete or overwrite a file without reading it first.
- Re-read any article immediately before editing it.
- Never modify `_absorb_log.json` or anything under the code tree.
- Rebuild `_index.md`, `_backlinks.json`, `_grades.json` only at the end of a command.
